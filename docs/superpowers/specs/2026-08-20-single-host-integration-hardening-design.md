# 单机 Compose 全链路加固与联调设计

## 1. 目标

把当前仓库收敛为一套可在 12GB 内存单机上通过 Docker Compose 一键启动、可完成毕业设计演示且关键业务数据可信的系统。

完成后必须能够演示：

```text
注册/登录 → 浏览房源 → 创建订单 → 支付/分期 → 双方签署合同
→ 查看通知 → 退租退款 → 房源恢复可租
```

本设计吸收 `2026-08-20-payment-safety-optimization-design.md`，并把范围扩展到前端、Gateway、用户、房源、订单、支付、合同、通知、数据库、中间件和端到端验收。

## 2. 边界

本轮目标是单宿主机上的可靠演示，不宣称生产级跨主机容灾。

包含：

- 统一外部入口与可信身份传递；
- 修复资金、订单、合同和房源状态一致性；
- 修复前后端接口和字段契约；
- 为关键 RocketMQ 事件增加可靠投递与幂等消费；
- 补齐全新环境数据库初始化、MariaDB 主从、健康检查和持久卷；
- 建立后端、前端、Compose 和真实 E2E 验收链。

不包含：

- K3s/Kubernetes/HPA；
- 多宿主机自动故障转移；
- 多 Broker RocketMQ 集群；
- 跨机房灾备和生产级密钥托管平台；
- 全量重写现有微服务。

## 3. 实施原则

1. 资金和权限问题优先于性能与展示优化。
2. 每个阶段先写失败测试，再进行最小实现。
3. 每个阶段独立提交、独立验证，失败时不叠加下一阶段。
4. 前端金额只用于展示，最终金额必须由后端计算并返回。
5. Redis 锁用于并发控制，数据库唯一约束和条件更新负责最终一致性。
6. 构建成功、静态配置通过和真实 E2E 必须分别报告，不互相替代。

## 4. 目标入口与权限架构

目标请求链：

```text
浏览器 → Nginx:80 → Gateway → 业务服务
                         └→ 校验 JWT 并注入可信身份
```

### 4.1 外部端口

- 宿主机默认只开放 Nginx `80` 和明确需要展示的管理端口。
- Gateway、用户、房源、订单、支付、合同和通知服务只使用 Compose `expose`。
- MySQL、Redis、Nacos、RocketMQ 的宿主机端口只用于本地运维，并绑定回环地址或通过 profile 显式开启。

### 4.2 Gateway 身份处理

Gateway 成为身份验证的最终入口：

- 先删除客户端传入的 `X-User-Id`、`X-User-Role`；
- 验证 `Authorization: Bearer <JWT>` 的签名和过期时间；
- 从 JWT claims 注入可信用户 ID 和角色；
- 登录、注册、健康检查、房源公开列表/详情进入白名单；
- 其余外部接口必须登录；
- 支付成功、退款成功、房源内部状态更新、合同生成等服务间端点加入外部拒绝列表。

Nginx保留限流、反向代理和内部路径拒绝，不再作为唯一身份可信边界。这样本地开发即使直接访问 Gateway，也不能通过伪造身份头提权。

### 4.3 业务归属校验

- 合同签署不再接受前端提供的 `userId` 和 `userType`；后端根据认证用户与合同双方关系判断身份。
- 合同详情、列表、下载必须属于当前租客、房东或管理员。
- 通知列表、未读数、已读和删除统一使用认证用户，不接受 query `userId`。
- 房源写操作校验房东归属；管理员操作依据可信角色。
- 内部服务调用通过直连服务名访问，不经过外部 `/api/**` 路由。

## 5. 金额模型与状态机

### 5.1 金额定义

统一采用：

```text
总租金 = 月租 × 租期月数
订单总额 = 总租金 + 押金
非分期应付 = 订单总额
分期首期 = 押金 + 首月租金
后续每期 = 一个月租金
所有分期金额之和 = 订单总额
```

前端仅提交订单号、支付方式和可选分期 ID。后端从订单和分期计划计算金额，拒绝零金额、负金额、越权分期和不属于该订单的分期 ID。

### 5.2 订单状态

允许的核心流转：

```text
PENDING_PAYMENT → PAID → RENTING → COMPLETED
       │            │        │
       └→ CANCELLED └→ REFUNDED
```

- 首次全额或首期支付成功后进入 `PAID`；
- 双方完成合同签署后进入 `RENTING`；
- 已取消、已退款和已完成订单不能被支付回调恢复；
- 所有状态更新使用“当前状态 + 目标状态”的数据库条件更新；
- 订单超时任务恢复启用，过期未支付订单转为 `CANCELLED` 并释放房源占用。

### 5.3 房源状态

- 创建订单时锁定并再次检查房源可租状态；
- 首次支付成功后房源转为 `RENTED`；
- `RENTED` 房源不能由房东直接重新上架或删除；
- 退款/退租完成后才允许恢复 `AVAILABLE`；
- 状态参数使用枚举，不接受任意字符串。

## 6. 支付与退款

### 6.1 创建支付单

幂等键：

```text
orderNo:FULL
orderNo:installmentId
```

流程：

1. 获取 `payment:create:lock:{idempotencyKey}`；
2. 查询已有支付单；
3. 已有 `PENDING` 时返回原支付单；
4. 已有 `SUCCESS` 时按已支付处理；
5. 无记录时重新验证订单、计算金额并插入；
6. 数据库唯一索引作为并发兜底。

### 6.2 执行支付

- 使用 `payment:execute:lock:{paymentNo}`；
- 重新验证支付单归属、订单状态、过期时间和分期状态；
- 已成功支付的重复请求按幂等成功返回；
- 租客扣款、房东入账、流水和支付状态处于同一本地事务；
- 支付状态使用条件更新，只有 `PENDING → SUCCESS` 成功一次。

### 6.3 退款

- 使用 `payment:refund:lock:{paymentNo}`；
- 只有原付款人或经过明确授权的退租编排流程可以退款；
- 只有 `SUCCESS → REFUNDED` 可以产生一次资金变动；
- 分期订单按实际已支付记录计算可退总额，不能只退第一笔；
- 支付服务返回实际退款金额和退款记录号；
- 重复退款返回原结果，不再次生成流水。

订单和合同只有在支付服务明确返回业务成功后才能进入退款终态。支付已成功但后续订单/合同更新失败时，用户重试会读取幂等退款结果并继续完成后续状态更新。

## 7. 可靠事件与 RocketMQ

关键事件至少包括：

- `PAYMENT_SUCCEEDED`；
- `CONTRACT_COMPLETED`；
- `REFUND_SUCCEEDED`；
- 通知类业务事件。

发送侧在本地事务写入 outbox：`event_id、event_type、aggregate_id、payload、status、retry_count、next_retry_time`。后台发布成功后标记 `SENT`，失败按有限退避重试。

消费侧使用 `consumer_group + event_id` 唯一键判重：

- 业务处理与消费记录处于同一本地事务；
- 处理失败必须抛出异常，不能只记录日志；
- 超过重试次数进入 DLQ，并提供查询与人工重放脚本；
- 一个事件需要写多条通知时必须整体幂等。

单机 RocketMQ Broker 增加持久卷和健康检查，但文档明确标注为单 Broker 持久化，不宣称 Broker 高可用。

## 8. 合同与通知

### 8.1 合同

- 只有订单首次支付成功后生成一份合同，订单号建立唯一约束；
- 单机 JVM `synchronized` 改为数据库条件更新或合同粒度分布式锁；
- 第一方签署后状态为 `LANDLORD_SIGNED` 或 `TENANT_SIGNED`；
- 第二方仍可看到签署入口；
- 双方完成后发布 `CONTRACT_COMPLETED`，订单从 `PAID` 转为 `RENTING`；
- 下载通过受保护的同源 Blob 请求完成，不使用客户端绝对 `localhost` 地址。

### 8.2 通知

- 所有角色都显示消息入口和未读数；
- 查询、已读和删除操作全部绑定认证用户；
- 内部发送接口不经公网 Gateway；
- MQ 消费按 event ID 幂等，失败允许 Broker 重试。

## 9. 前端契约与稳定性

### 9.1 统一 API 环境

- Vite 使用 `VITE_API_TARGET`；
- 本地默认目标为 `http://localhost` 的 Nginx 入口；
- 生产构建使用相对 `/api`；
- 不再在源码中固定 `192.168.24.129` 或下载地址。

### 9.2 会话

提供唯一的安全会话解析函数：

- JSON 损坏、字段缺失或 token 缺失时清理本地状态并按未登录处理；
- Router、App 和页面不得各自直接 `JSON.parse`；
- 401 统一清理会话并跳转登录。

### 9.3 页面行为

- 支付页从订单详情选择下一条 `UNPAID` 分期并提交 `installmentId`；
- 页面金额以创建支付单响应为最终确认；
- 退款弹窗调用后端预览，成功提示使用后端实际退款结果；
- 钱包刷新使用 `every(Boolean)` 判断整体成功；
- 分页统一使用 `pageNum/pageSize`；
- 第二签署人可以继续签署合同；
- 所有写按钮在请求期间禁用，并在 `finally` 恢复；
- 删除无后端实现且无调用方的支付 API 定义；
- 前端需要的分期列表通过带订单归属校验的订单详情返回，不再开放内部 `/installments` 路径。

## 10. 数据库和 Compose

### 10.1 全新环境初始化

主库初始化必须创建：

- `apartment_db` 及全部业务表；
- `nacos_config` 及当前 Nacos 版本所需表；
- 最小权限应用用户、Nacos 用户和复制用户；
- 必要唯一索引、联合索引和历史数据兼容迁移。

迁移脚本必须可重复执行。发现历史重复支付、重复合同或其他资金冲突时必须中止并输出冲突，不自动删除业务数据。

### 10.2 MariaDB 主从

- 主库启用 GTID、row binlog、`log_slave_updates`；
- 从库启用 MariaDB `read_only=1`，应用账号不授予 `READ ONLY ADMIN`，避免把 MySQL 专属的 `super_read_only` 配置误用于 MariaDB 10.11；
- 初始化任务等待主库健康后执行幂等复制配置；
- 验收要求 IO/SQL 线程正常、延迟在阈值内、写入探针可复制；
- 单机主库故障时允许读路径继续，写路径明确失败；本轮不做自动主库提升。

### 10.3 Redis、Nacos、RocketMQ

- Redis master/slave 挂载持久卷并增加健康检查；
- Sentinel 验证容器级主从切换，但标注单宿主机边界；
- Nacos 数据库先初始化，再启动 Nacos 节点；
- RocketMQ store/logs 挂载持久卷，显式创建 Topic 和消费组；
- 密码、JWT secret、主机地址通过 `.env`/Secret 注入，示例文件不提供可用于生产的弱默认值。

### 10.4 资源预算

核心业务栈默认适配 12GB 内存。Prometheus/Grafana/cAdvisor 通过 `monitor` profile 启动。核心一键命令为：

```powershell
docker compose up -d --build --wait
```

完整观测命令为：

```powershell
docker compose --profile monitor up -d --build --wait
```

Prometheus 使用可发现的服务目标，不绑定 `*-1` 容器名；扩容脚本必须使用动态项目路径、检查 Compose 返回码，并加入连续窗口和冷却时间。

## 11. 错误处理

- 对外响应继续保持 `{code,message,data}`，同时为认证、权限、参数和服务异常使用正确 HTTP 状态；
- Feign 调用必须同时检查 HTTP 状态和业务 `code`；
- 远程调用失败不能被当作业务成功提交最终状态；
- 关键状态更新检查受影响行数，零行视为并发冲突；
- 日志记录 trace ID、event ID 和业务编号，不记录 token、密码或完整敏感数据；
- 前端不根据本地数组、旧余额或请求已发出来判断业务成功。

## 12. 测试设计

### 12.1 后端单元与集成测试

必须新增：

- Gateway：伪造身份头、无 token、过期 token、普通用户冒充管理员；
- 用户：登录与角色 claims；
- 订单：金额守恒、状态转移、超时取消、取消后支付拒绝；
- 支付：创建幂等、重复执行、并发退款、越权退款、非法充值；
- 合同：冒签拒绝、第二方签署、越权详情/下载；
- 通知：用户归属、删除权限、MQ 幂等与失败重试；
- Testcontainers：MySQL/Redis/RocketMQ 关键集成路径。

### 12.2 前端测试

引入 Vitest，至少覆盖：

- 损坏会话解析；
- API 参数映射；
- 分期选择与金额展示；
- 钱包刷新整体结果；
- 第二签署人按钮；
- 重复提交 guard。

### 12.3 真实 E2E

在真实 Compose 服务上验证：

1. 注册或登录租客、房东；
2. 房东发布房源；
3. 租客创建全额订单并支付；
4. 双方完成合同签署；
5. 通知最终到达且无重复；
6. 创建分期订单，确认首期金额和分期状态；
7. 执行退租退款，确认双方余额、订单、合同和房源状态；
8. 重复支付、重复退款、越权访问均被拒绝或幂等处理。

## 13. 分阶段实施

### 阶段 A：权限与资金 P0

Gateway 身份、内部端点隔离、合同/通知归属、金额模型、支付幂等、退款幂等和状态机。

### 阶段 B：前端与跨服务契约 P0

分期参数、退款预览、会话解析、签约、通知入口、分页、下载和失败响应处理。

### 阶段 C：可靠事件与 Compose P1

Outbox/消费幂等、RocketMQ 持久化、数据库初始化、主从复制、健康检查、环境变量和监控目标。

### 阶段 D：自动化验收 P1

补齐单元/集成测试、前端测试、真实 E2E、故障恢复和演示证据。

## 14. 完成标准

只有同时满足以下条件才算本轮完成：

- 全仓 Maven 测试通过；
- 前端测试和生产构建通过；
- `docker compose config -q` 通过；
- 全新 volume 下 `docker compose up -d --build --wait` 成功；
- MySQL 复制、Redis Sentinel、RocketMQ 重启持久性验证通过；
- 登录到通知及退租退款两条 E2E 通过；
- 重复支付、重复退款、越权访问和损坏会话负向用例通过；
- 未通过的生产级能力明确记录为边界，不用静态配置冒充运行证据。
