# 支付模块最小安全优化设计

## 目标

在不引入 Outbox、事务消息或完整支付状态机的前提下，增强支付模块对重复创建、重复执行、并发退款、越权退款和非法充值的防护，并通过数据库约束为应用层锁与状态判断提供最终兜底。

## 范围

本次修改限定在 `apartment-payment-service`：

- 创建支付单幂等处理；
- 执行支付状态保护；
- 退款并发保护和付款人鉴权；
- 演示充值金额校验；
- 账户初始化接口解耦；
- 支付与交易查询索引；
- 对应的自动化测试。

本次不引入可靠消息表、RocketMQ 事务消息或跨服务补偿任务。支付成功通知订单服务失败时的可靠投递问题作为后续演进项保留。

## 方案选择

采用“分布式锁 + 业务状态判断 + 数据库唯一幂等键”的组合方案。

仅依赖前端防抖无法处理多端操作、网络重试和直接调用接口；仅依赖 Redis 锁也无法覆盖 Redis 故障、锁租期失效或绕过应用入口的情况。数据库唯一约束负责最终拒绝重复数据，应用层负责返回可理解的业务结果。

## 数据模型

在 `payment` 表增加非空字段 `idempotency_key`，格式为：

```text
订单号:FULL
订单号:分期ID
```

为该字段建立唯一索引 `uk_payment_idempotency_key`。同一订单的全额支付只能对应一个支付单，同一分期也只能对应一个支付单。失败后继续使用原支付单执行重试，不重复创建新支付单。

补充以下联合索引：

- `payment(order_no, payment_status)`：支持按订单和状态检查支付记录；
- `account_transaction(user_id, create_time)`：支持用户交易记录倒序查询。

同步修改支付服务的建表脚本，并新增一个显式、可重复执行的迁移脚本供已有数据库升级。迁移先为历史支付记录回填幂等键；若历史数据中已经存在同一订单或分期的重复支付单，脚本必须检测后中止并输出冲突记录，不得擅自删除资金数据。当前 Compose 不会自动执行各业务模块的 `schema.sql`，因此迁移脚本作为部署前的明确步骤执行。

## 创建支付单流程

1. 校验用户、订单号、支付方式和分期参数。
2. 生成幂等键并获取 `payment:create:lock:{idempotencyKey}` 分布式锁。
3. 按幂等键查询已有支付单。
4. 已有 `PENDING` 支付单时返回原支付单信息，不再次插入。
5. 已有 `SUCCESS` 支付单时返回“订单已支付”业务错误。
6. `FAILED` 或 `REFUNDED` 等其他状态返回“该支付场景已有历史支付单”的明确业务错误，不在本次最小方案中创建第二条记录。
7. 无记录时验证订单、计算服务端金额、检查余额并插入支付单。
8. 数据库唯一约束冲突时重新查询原支付单并按相同规则返回，覆盖极端并发。

支付金额始终从订单服务返回的数据计算，不接受前端传入金额。

## 执行支付流程

继续使用 `payment:execute:lock:{paymentNo}` 锁。只有归属当前用户且状态为 `PENDING` 的支付单允许执行。重复请求遇到 `SUCCESS` 状态时按幂等成功处理，不重复扣款；其他状态返回明确错误。

支付单状态更新必须检查受影响行数。余额扣减、房东入账和支付单状态更新继续处于本地事务中。订单服务通知仍是跨服务同步调用，本次不宣称具备完整分布式事务一致性。

## 退款流程

退款增加 `payment:refund:lock:{paymentNo}` 分布式锁。进入事务后重新读取支付单，并执行：

- 支付单必须属于当前用户；
- 只有 `SUCCESS` 状态允许退款；
- `REFUNDED` 状态按幂等成功处理，不再次转账；
- 房东扣款、租客入账和支付状态更新在同一本地事务中完成。

按订单号退款最终仍调用同一套付款人鉴权和退款锁逻辑，避免两条入口产生不同行为。

## 充值与接口解耦

演示充值金额要求：

- 必填；
- 大于等于 `0.01`；
- 小于等于 `100000.00`；
- 最多两位小数。

控制器继续使用 `@Valid` 触发统一参数校验。`AccountService` 增加账户初始化方法，由 `PaymentServiceImpl` 通过接口调用，删除对 `AccountServiceImpl` 的强制类型转换。

## 错误处理

- 获取锁超时返回可重试的业务提示；
- 用户不匹配返回无权操作；
- 唯一键冲突不直接暴露数据库异常，而是读取并返回已有支付单；
- 远程订单数据缺失、金额非正数或房东信息缺失时中止事务；
- 日志只记录业务编号和用户编号，不记录认证信息或敏感凭据。

## 测试策略

使用 TDD，先写测试并确认其因目标行为尚未实现而失败，再写最小实现：

1. 同一幂等键重复创建时返回原 `PENDING` 支付单且不重复插入；
2. 已成功支付的幂等键拒绝创建新支付单；
3. 重复执行已成功支付单不重复扣款；
4. 非付款人退款被拒绝；
5. 已退款支付单重复退款不重复转账；
6. 退款锁未获取时不执行退款；
7. 充值金额为空、非正数、超上限或超过两位小数时校验失败；
8. 原有支付成功和退款成功测试保持通过。

先运行支付模块定向测试，再运行 Maven 全仓测试。若环境依赖导致集成验证无法进行，必须明确记录边界，不将静态检查描述成运行通过。

## 验收标准

- 同一订单或分期的重复创建请求只产生一条支付记录；
- 同一支付单重复执行不会重复扣除租客余额或增加房东余额；
- 非付款人不能发起退款；
- 同一支付单重复退款不会产生第二次资金变动；
- 非法充值金额在进入服务层前被拒绝；
- 支付模块测试和全仓既有测试均无回归；
- 新库建表脚本包含新字段和索引；已有库迁移脚本可重复执行，并在发现历史幂等冲突时安全中止而不删除数据。

## 已知边界

支付服务本地事务不能原子覆盖订单服务。订单回调请求丢失、超时或成功响应丢失时，仍可能出现跨服务状态短暂或长期不一致。该问题需要后续通过本地 Outbox、事件幂等消费和补偿任务解决，不属于本次最小安全优化的完成范围。
